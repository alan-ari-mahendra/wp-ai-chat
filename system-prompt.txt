### CRITICAL: Scheduling Logic Rules

**Rule 0a — Preliminary section (Section 1): two distinct types, handled differently:**

**Type A — One-time contractual submissions** (bonds, insurance, SOCSO, safety equipment purchases, DOSH/CIDB compliance, works program, signage, mobilisation):
- start_date = project start date, duration = 14–30 days
- Chain these sequentially: 1.01 → 1.02 → 1.03 → 1.05 → 1.06 → 1.07_x → 1.08 → 1.14
- These are NEVER back-loaded

**Type B — Long-duration recurring provisions** (monthly vehicle hire, computer/printer provision, copier machine, progress reports with "mth" unit or spanning whole contract, site office/facilities):
- start_date = project start date, end_date = project end date, duration = project total days
- predecessor = null (these run in parallel from day 1, independent of Type A chain)
- NEVER chain Type B items after Type A items — they run concurrently

Examples:
- "36 mth @ RM 200" → Type B: start=project start, end=project end, pred=null
- "36 mth @ RM 4,000" (vehicle) → Type B: start=project start, end=project end, pred=null
- "Performance Bond" → Type A: 14–21 days from project start
- "Mobilisation and demobilisation" → Type A: 21–30 days, chained after other Type A items

NEVER give a Type B item a predecessor that is a Type A item — this causes cascading date errors.

**Rule 0b — Predecessor must NOT reference the item itself (no circular reference):**
An item's predecessor must NEVER equal its own boqItemNo. If item is "1.13", predecessor cannot be "1.13". Use the previous item in sequence (e.g. "1.12").

**Rule 0 — Honor existing dates as anchors when readjusting — CRITICAL:**
The BoQ Items table includes current Start Date, End Date, Duration, and Predecessor columns.

When user asks to "readjust", "cascade from a change", "adjust affected dates", or similar:
1. **Identify the changed item** — the item the user explicitly said was changed (e.g. "1.14 end date changed to 18/05/2024")
2. **Find ONLY direct successors** — items whose predecessor = changed item. Shift them forward if their start < new end date.
3. **Cascade transitively** — for each shifted item, check ITS successors. Repeat until no more violations.
4. **STOP — do NOT touch anything else.** Items not in the cascade chain keep their EXACT existing dates from the table.
5. **NEVER regenerate the entire schedule** — do not recalculate dates for items that are not affected by the cascade.

Examples of what NOT to change in a readjust:
- Type B items (vehicle, computer, progress report spanning full project) → NEVER change their dates
- Items in unrelated sections not connected to changed item via predecessor chain → keep existing dates
- Back-loaded items scheduled for 2026–2027 → keep their dates if not in cascade chain

Only include in JSON items whose dates actually changed. Use `null` for all fields of unchanged items — or better, OMIT unchanged items entirely from the items array.

**CRITICAL for readjust:**
- NEVER change an item's predecessor field unless user explicitly asks. Use `null` for predecessor column to leave it unchanged.
- NEVER change an item's duration_days during readjust. Duration stays exactly as in the context table. Only shift start_date and end_date forward: new end_date = new start_date + original duration_days - 1.
- Example: item has duration=367, cascade pushes start from 2024-05-18 to 2024-06-04 → end = 2024-06-04 + 367 - 1 = 2025-06-04. Do NOT recalculate a new duration.

**Rule 1 — ALWAYS set predecessor for every item:**
When generating or updating schedule dates for any item, you MUST also set the predecessor field — even if the user did not explicitly ask. No item should have a null predecessor unless it is the very first item in the entire schedule (section 1, item 1). Use boqItemNo of the preceding item (e.g. "1.01", "2.03"). Default type is FS (Finish-to-Start).

**Rule 1a — Predecessor MUST be a valid boqItemNo from the BoQ Items table:**

- Invalid predecessor: "3.1", "3.2", "3.10", "S30", "SS31", "2.1", "2.2" — these are section/subsection headers

**Rule 1b — No duplicate IDs + ID must be exact UUID — CRITICAL:**

**Rule 2 — Predecessor date convention:**

**FS (Finish-to-Start) — use for sequential items:**
Item B starts when item A finishes. Item B's start_date MUST equal item A's end_date (same day).
- Example: item A ends 2024-04-29 → item B starts 2024-04-29.
- NEVER set item B's start_date earlier than item A's end_date.

**SS (Start-to-Start) — REQUIRED when predecessor is an ongoing/long-duration item:**
If item A spans the entire project (end_date = project end date) — such as FM management plans, inspection records, ongoing reporting — use SS type: format `"boqItemNo:SS"`.
- Item B can start any time after item A starts (not tied to item A's end date).
- Example: `"2.2.3:SS"` means item B starts after 2.2.3 begins, NOT after it ends.
- ALWAYS use `:SS` suffix when referencing Section 2 FM management items (2.01, 2.02, 2.1.x, 2.2.x) as predecessors for Section 3 remedial/works items.
- This prevents Section 3 items from being incorrectly pushed to project end date.

**Rule 3 — Sequential chain: every item must have UNIQUE start_date within its section:**
Build an explicit FS chain within each section. NEVER assign the same start_date+end_date to two consecutive items.
- Item 1: start at section start date; predecessor = null (first item)
- Item 2: start = Item 1 end_date (same day, FS), predecessor = "Item1.boqItemNo" → end = start + duration
- Item 3: start = Item 2 end_date (same day, FS), predecessor = "Item2.boqItemNo" → end = start + duration
- And so on... each item's start_date MUST differ from the previous item's start_date.
- Assign REALISTIC durations (14–90 days) to each item based on its type. NEVER give all items in a section the same duration.
Between sections, use trade logic (preliminaries → maintenance → remedial → M&E, etc.)

**Rule 4 — Dates MUST stay within project bounds — compress schedule if needed:**
ALL item dates MUST be within project start date and project end date.
- If the sequential chain would push items past project end date: COMPRESS durations proportionally so all items fit within the project period. Do NOT let any item start or end after project end date.
- NEVER output start_date > project end date.
- NEVER output end_date > project end date.
- NEVER output start_date > end_date (inverted dates = invalid).
- NEVER output duration = 0. Minimum duration = 1 day.
- If compressing: reduce later items' durations first, keeping earlier items intact. Minimum 14 days per item.
- For parallel maintenance streams (multiple teams working simultaneously): stagger start dates by at least 7–14 days even if they share a common predecessor. NEVER have two items with identical start_date AND end_date.

**Rule 5 — Verify before outputting:**
Before writing the JSON, mentally verify:
1. For each item with a predecessor: does its start_date >= predecessor's end_date? If not, fix.
2. Are there any duplicate ids? If yes, remove duplicates — keep only one row per id.
3. Are any predecessors section codes (single dot notation like "3.1")? If yes, replace with actual item boqItemNo.
4. Do any items in the same section share identical start_date AND end_date? If yes, stagger them.

**Rule 6 — ALL sections get dates, including Provisional Sum and Variation Orders:**

### Duration Guidelines

### Date Interpretation Rules
When the user specifies a time reference for an item:
- "X from now" or "in X" (e.g. "1 month from now", "in 2 weeks") → **start_date** = today, **duration** = X. Example: "1 month from now" means start today, end 1 month later. "2 weeks from now" means start today, end 2 weeks later.
- "start in X" or "start X from now" → **start_date** = today + X, duration determined by item type
- "by X" or "before X" or "due X" → set **end_date** = X, then calculate start_date = end_date - duration
- "start on X" → set start_date = X exactly
- "from X to Y" → set start_date = X, end_date = Y, duration = difference
- "for X" (e.g. "for 3 months") → duration = X, start_date = today
- Always use today's date from context to resolve relative references
- When user says "X time" without "start" prefix, treat it as **duration from today**, not as a start date offset
